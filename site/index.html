O problema

Como um aviso se perde

A plataforma avisa a loja. Se a loja não atende, o aviso pode ser descartado sem ninguém saber.

Quando dá certo

1Cliente pagaO comprador paga o pedido com Pix, cartão ou boleto.
2Plataforma manda o avisoEla envia um aviso automático: "pedido pago".
3Sistema da loja recebeO receptor da loja registra a venda e libera o pedido.

Quando o servidor da loja está fora do ar

1Cliente pagaO dinheiro entra.
2Plataforma manda o avisoNinguém responde do outro lado.
Loja não fica sabendoO pedido fica parado, como se não tivesse sido pago.

Segundo a documentação pública

Se o servidor da loja não responde, a plataforma tenta de novo até 4 vezes, esperando até 5 s por resposta em cada uma, com a última em até 6h30. Depois disso o aviso é descartado permanentemente, sem notificar ninguém.

Isto é o que a documentação descreve, não uma medição deste projeto.

Documentação e painel do app dizem tempos diferentes

A documentação fala em 5 s de espera por tentativa. O painel do app, na plataforma, fala em 10 s. Nos experimentos abaixo a plataforma esperou mais do que isso sem cortar (ver "Um app lento atrasa os avisos seguintes"); daqui não dá para saber qual é o limite real.

A saída

Dá para descobrir o que se perdeu perguntando à API, que é a fonte da verdade. O conferidor compara os avisos que chegaram com o que a API diz. Se a API diz pago e o aviso não chegou, ele aponta.

Antes de publicar um app, a plataforma testa uma lista pública de cenários. O testador roda essa lista no seu sandbox e diz, cenário por cenário, o que aconteceu.

Os quatro resultados e o que fazer

Passou

Todos os avisos esperados chegaram ao seu app, e a API confirma o mesmo status.

O que você faz: Nada. Siga para o próximo cenário.

Falhou

A API mostra que o fato aconteceu (por exemplo, o pedido foi pago), mas o aviso não chegou ao seu app em 10 minutos.

O que você faz: Veja se o seu app estava no ar e respondeu rápido. Confira o endereço de avisos cadastrado no painel. Depois rode python -m testador rejulgar: se o aviso chegou atrasado, o resultado muda.

Inconclusivo

A plataforma ainda não terminou de processar este pedido (por exemplo, o estorno está em análise). Então é normal o aviso ainda não ter chegado. Não é erro do seu app.

O que você faz: Espere e confira de novo com python -m testador rejulgar. Se continuar assim, pergunte à plataforma quanto tempo leva esse processamento.

Não executado

A plataforma recusou uma etapa do teste (por exemplo, não aceita estorno de boleto pela API). O seu app nem chegou a ser testado neste cenário.

O que você faz: Não é falha do seu app. Leia o motivo. Se o cenário for exigido, descubra com a plataforma como ele é feito (no caso do boleto, a própria API pede que o estorno seja feito à mão).

Como usar

Como usar em 3 passos

Instalar, rodar, ler o resultado.

Antes de começar: Python 3.10 ou mais novo, nenhuma dependência. Um app próprio no sandbox da plataforma. Um túnel que deixe o seu computador receber avisos da internet.

Use só com o seu próprio app, no sandbox. Nunca aponte para a produção de terceiros.

  1. 1

    Instalar

    Copie .env.exemplo para .env e preencha o endereço do túnel e os dados do seu app. Depois:

    python -m conferidor.receptor
python -m conferidor.sandbox instalar

    O que esperar: O primeiro comando fica rodando e recebe os avisos (deixe esse terminal aberto). O segundo instala o seu app numa loja de teste.

  2. 2

    Rodar

    Em outro terminal:

    python -m testador rodar

    O que esperar: Ele cria 12 pedidos de teste (Pix e cartão 1x, CPF e CNPJ, compra e estornos) e espera até 10 minutos pelos avisos.

    Para boleto e cartão parcelado:

    python -m testador rodar --meios boleto,cartao_parcelado --nome boleto_3x

    Para ver o conferidor achando um aviso perdido: crie Pix de teste, pare o receptor, crie mais pedidos e confira.

    python -m conferidor.sandbox pix --quantos 3
python -m conferidor.sandbox conferir

  3. 3

    Ler o resultado

    python -m testador relatorio

    O que esperar: Um relatório em HTML com um selo por cenário. Se algum ficou inconclusivo, espere a plataforma processar e confira de novo, sem criar pedidos:

    python -m testador rejulgar

Teste extra: o seu endereço aguenta aviso repetido e fora de ordem?
python -m testador resistencia --alvo URL

Rode contra um segundo receptor (--porta 8081 --banco outro.db) para não misturar pedidos fictícios.

O repositório do código é privado. Código disponível sob pedido ao autor.

Limites

O que isto não prova

Tudo aqui foi medido em ambiente de teste. Leia antes de tirar conclusão.

Ressalvas

  • Tudo foi medido no sandbox, que pode se comportar diferente da produção.
  • Um app só, o do próprio autor.
  • Uma rodada de cada experimento (o testador teve uma rodada anterior com regra antiga, não exibida).
  • Janela de reentrega ainda aberta na conferência de 14/10 (feita cerca de 23 min após os pedidos). Zero nova tentativa ainda não é conclusão.
  • A observação de reentrega de 13/10 tem 2 pedidos e a falha foi um 502; a documentação não diz se 502 gera nova tentativa.
  • A janela de espera do testador é de 10 minutos; aviso pode chegar depois.
  • O testador não é a homologação e não dá aprovação.
  • O teste de resistência mede só a resposta e o tempo, num endereço local; o que o app faz por dentro não é visível.
  • Projeto independente, sem vínculo com a plataforma, sem dado de cliente.

O que não dá para conferir de fora

  • Código de rastreio: A consulta de pedido não devolve o rastreio cadastrado.
  • Descrição que aparece na fatura do cartão: A consulta de pedido não devolve esse campo.
  • IP do comprador: Coletado pelo script da plataforma no navegador; a consulta de pedido não devolve.
  • URL de instalação: A plataforma já oferece uma ferramenta própria para testar (guia "Valide sua URL de validação").
  • Logo, descrição e e-mail de suporte do app: Conferência visual, feita pela equipe da plataforma.

Glossário

Aviso (webhook)
Mensagem automática que a plataforma manda para o sistema da loja quando algo muda num pedido, como "pedido pago".
Receptor
O programa da loja que recebe os avisos num endereço da internet. Se ele estiver desligado, o aviso não entra.
Sandbox
Ambiente de teste da plataforma. Dinheiro de mentira, pedidos de mentira. Pode se comportar diferente do ambiente real.
Status na API
O que a plataforma responde quando você pergunta sobre um pedido. É a fonte da verdade.

Quando o aviso falha, a plataforma deveria tentar de novo. A documentação pública fala em até 4 tentativas, a última em até 6h30.
Janela de espera
Quanto tempo o testador espera os avisos antes de julgar: 10 minutos. Um aviso pode chegar depois disso.
Estorno (total ou parcial)
Devolver ao comprador o valor inteiro (total) ou só uma parte (parcial).
Homologação
Revisão que a plataforma faz antes de aceitar um app na loja de aplicativos. Este site não faz nem substitui essa revisão.
